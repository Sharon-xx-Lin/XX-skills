# PRD 原型图与需求 Demo

## 这个 skill 解决什么问题

产品经理拿 AI 生成需求原型时，产出常常「一眼就是 AI 做的」，拿给设计和研发看反而引起反感。但成因需要说准，否则会用错力气。

**模型的看图模仿能力其实不弱** —— 给它一张截图，它能采出接近真实的主色、做出像样的表格。实测对比中，无约束的一方单次生成的视觉还原度也不低。真正的问题在四处，都不是审美能力问题：

1. **配色每次都在重新发明。** 实测同一产品的第二个需求：无约束的一方只有 4 个 token 与第一个需求同名（2 个取值还不一致），另造了 28 个新颜色。单看每次都协调，放在一起就不是一个产品了。团队感受到的「AI 味」很大程度是这种**跨需求的不一致**。
2. **颜色绕过 token 写死。** 实测无约束方在 `:root` 之外有 55 处硬编码色值，含几个连自己 token 里都没有的颜色。首次看不出问题，改几轮就漂回模型默认审美。
3. **交付形态不可用。** demo 做成多文件依赖时，生成方自测正常，但 PM 把主文件发到群里，同事打开一片空白。
4. **画的不是界面，是需求说明。** 最容易跑偏的一点 —— 在画板上排一堆写着「区域 A：KPI 卡 ×4」「需新增」的文字卡片，看着像图，其实是 PRD 的图形化排版，评审时依然说不清交互。

所以本 skill 的重点不是「教模型模仿」，而是**把设计语言固化成可复用可校验的档案，并保证画出来的是真界面、交付出去真能用**。

## 两个产物，职责不同

| 产物 | 是什么 | 给谁看 |
|---|---|---|
| **逐帧线框图**（SVG） | 真实界面的等比还原，按交互顺序逐帧铺开 | 团队评审对齐交互流程 |
| 可交互 **HTML demo** | 单文件、双击即开、能点 | 研发和设计看「长什么样、怎么动」 |

两者共享 **UI 档案**（保证视觉同源）和 **画面清单**（保证画的是同一批界面）。不做同源渲染 —— 那需要一个同时输出绝对坐标 SVG 和流式 HTML 的中间层，抽象必然退到最小公共集，线框图那边的限制（协作白板普遍不支持阴影、圆角被量化）会被抬上来把 HTML 的高保真拖下去。

## 工作流

```
① 收素材（PRD + 截图） → ② UI 档案 → ③ 画面清单 → ④ 逐帧线框图 → ⑤ HTML demo → ⑥ 自检
                          可复用资产      澄清关口      SVG 图纸         单文件        机械校验
```

档案（②）做一次长期复用，后续需求从 ③ 开始。

### 先判断这是第几次

**开工第一件事：查工作目录下 `artifacts/ui-profiles/` 有没有这个产品的档案。** 这决定走哪条路，也决定要向用户要什么。

| 情况 | 路径 | 要向用户说清的 |
|---|---|---|
| **没有档案**（首次） | ① → ② → ③ → ④ → ⑤ → ⑥ | 需要 3~5 张产品截图建档案；这一步做完长期复用。档案质量决定后面所有产出「像不像」，值得先花时间 |
| **有档案** | ① → ③ → ④ → ⑤ → ⑥ | 直接开始，不要重复采样。只在遇到档案没覆盖的控件时增补 |

首次建档案时**主动问一句有没有更强的素材** —— 前端代码仓库（可直读真实 CSS 变量）、已知组件库（Arco / Semi / Ant Design / TDesign）、设计规范文档。这些比截图采样准得多，有的话档案质量会高一个档次。

**首次的期望要说清**：档案只覆盖截图里出现过的控件，没出现的靠推导、需要后续校正。别让用户以为一次就能沉淀出完整设计系统。

## ① 收素材

**PRD 决定画什么，截图决定长什么样。** 两者缺一不可 —— 只有截图会导致靠猜编需求，只有 PRD 会导致画出通用 UI。

**PRD**：本地 Markdown / 纯文本文件，或直接粘贴进对话。如果你的团队用在线文档（飞书、Notion、Confluence 等），先把正文取出来 —— 有对应的读取工具就用，没有就复制粘贴，这一步不影响后续流程。

读 PRD 时重点抽取，其余略读：
- 功能范围与用户入口
- **页面与状态清单**（有哪些界面、每个界面有哪些状态）
- **字段名与真实取值**（demo 数据的来源，直接决定真实感）
- 交互规则、边界与异常
- **PRD 没写清的地方** —— 这些会成为画面清单里的「待确认」

PRD 里常附交互设计图或设计稿链接，**这是最直接的界面依据，优先用**。在线文档里的图片先导出到本地再读。

**截图**：理想是同产品 3~5 张，覆盖列表页、表单/详情页、含弹窗或 hover 态的页面、空状态。只有 1 张也能做，但要说明档案只覆盖出现过的控件。

档案存在你的工作目录 `artifacts/ui-profiles/{产品名}/`、按产品隔离，**不要放进 skill 目录** —— 不同人负责不同产品，档案必须彼此独立，也不该随 skill 分发。

## ② UI 档案

用 `scripts/sample_ui.py` 做像素采样。**不要靠眼睛估颜色** —— 肉眼对相近色完全不可靠，而颜色错一点点「像不像」就崩了。

```bash
python3 scripts/sample_ui.py --image 截图.png --list-points        # 点位建议
python3 scripts/sample_ui.py --image 截图.png --auto               # 调色板快速摸底
python3 scripts/sample_ui.py --image 截图.png --spec points.json --out t.json
```

`points.json` 的格式（`scale` 用于按比例缩放过的截图，1.0 即原图）：

```json
{
  "scale": 1.0,
  "points": [
    {"name": "页面主背景", "x": 900, "y": 500, "role": "bg"},
    {"name": "一级文字",   "x": 262, "y": 331, "role": "text"},
    {"name": "主色-按钮",  "x": 1512, "y": 60, "role": "accent"},
    {"name": "表格行分隔线", "x": 700, "y": 420, "role": "line",
     "horizontal": true, "span": 25, "group": "border"}
  ]
}
```

`role` 决定采样策略（见下表）。`line` 需给 `horizontal`：横线填 `true`（脚本垂直扫描穿过它），竖线省略。同语义的点标同一个 `group`，脚本会验证收敛性。

**坐标怎么定：不要凭感觉猜。** 先用图片查看器读出像素坐标，或者按下面的方法让脚本帮你定位；打完后看输出的警告 —— `置信度过低` / `亮度差过小，可能没扫到边框` 就是打偏了，挪几像素重采。这些警告是有效的，不要忽略。

```python
# 找结构边界：列均值方差突变处就是分栏线 / 面板边缘
from PIL import Image; import numpy as np
a = np.asarray(Image.open("shot.png").convert("L"), dtype=float)
var = a.var(axis=0)                      # 每列的纵向方差
print([x for x in range(1, len(var)) if abs(var[x] - var[x-1]) > 300][:20])
```

### 采样必须按元素角色分策略

最容易踩的坑：对所有元素统一用「取众数」，文字颜色会全部采成背景色 —— 文字笔画细、边缘有抗锯齿，7×7 窗口里背景像素永远占多数。

| 角色 | 策略 | 适用 |
|---|---|---|
| `bg` | 窗口内众数 | 背景、卡片底色、选中态底色 |
| `text` | 与底色**反差最大**的那一端（亮底取最暗、暗底取最亮） | 所有文字（笔画核心才是真值） |
| `accent` | **彩度最高**（`max-min`，不是 HSV 饱和度） | 品牌色、链接色、主按钮 |
| `line` | **扫描线法**：垂直穿过边框，找与底色反差最大的连续像素带 | 1px 发丝边框、网格线 |

后三条都是「先看底色，再定方向」，不能写死。原因见下节。

扫描线法尤其重要 —— 现代 UI 边框常只有 1px 且半透明，任何块采样都框不住。

**判断可信度**：给语义相同的点标同一个 `group`（如所有边框标 `group="border"`），每组采 3 点以上。脚本会算各通道极差，≤4 说明指向同一 token（真值）并给出中位数建议。不要按角色判断收敛 —— 文字本就三档、背景本就多层。

### 深色主题：方向全部反过来

**这是跨产品验证时唯一整片崩掉的地方。** 深色 UI 的文字是亮的、分隔线比底色亮，任何「取最暗」的硬编码都会把文字和线采成背景色 —— 而且不报错，静默产出一整套错值。

三条必须按底色亮度自动判方向（`sample_ui.py` 已实现，但自己加新逻辑时要守住）：

1. **文字**：先取窗口众数当底色，底色亮度 <128 就取最亮像素，否则取最暗。
2. **分隔线**：同理，取离底色更远的那一端，不是固定取暗端。
3. **品牌色**：用**彩度**（`max-min` 的绝对值）排序，不要用 HSV 饱和度 —— `(20,0,0)` 这种近黑噪点饱和度也是 1.0，在深色底上会被当成品牌色选中；它彩度只有 20，而真实品牌色彩度上百。

深色档案还有两件事和浅色不同：

- **中性文字常有四档**（正文/次要/元信息/极弱），比浅色多一档，因为暗底上更细的亮度差也能分辨。
- **层次靠背景递进，不靠边框**。成熟深色产品常常一条边框都没有：根黑 → 卡片 → 引用块 → 选中块，每层朝白提亮一点。扫描线法测出 Δ 只有 1~2 时，那不是采样失败，是**这个产品真的没有边框** —— 照实记进档案。

`use_profile()` 会按主背景亮度判 `theme` 并返回，深色档案缺失的层次色由主背景朝白推导，不会退回浅灰。

### 移动端：比例与密度都换一套

移动端不是「窄一点的桌面」：

- **画布按逻辑像素**（iPhone 375×812），不要用截图的物理像素。3x 截图量出来的值要除以 3。
- **一屏信息量少得多**：一屏 2~3 张内容卡、6~7 张列表项。桌面那套「表格行高 32px、一屏十几行」的密度直接套过来会挤成一团。
- **字号整体更大**：正文 15~16px、行高 1.6，桌面 B 端常用的 13~14px 在手机上偏小。
- **没有 hover**，交互态只有按压（整卡 `opacity: .8`）和选中。别画 hover 帧。
- **必画系统层**：状态栏（时间/信号/电量）、导航栏、底部标签栏。缺了这些一眼就不是手机界面。
- **转场有方向**：push 从右滑入、返回向左滑回，这个方向感是移动端的基本语汇。

移动端另有一套构件库 `scripts/mobile_kit.py`（`phone`/`statusbar`/`navbar`/`segbar`/`agg_card`/`post_card`/`tabbar`/`searchbar`/`empty_state`/`skeleton_card`/`grid_cell`/`seg_note`/`highlight_text`，外加 39 个移动端线性图标）。它在 `wireframe_kit` 之上，图纸语言构件仍从 `k` 取：

```python
import mobile_kit as m
m.k.use_profile("artifacts/ui-profiles/my-app")   # 先载入档案
print(m.load_extra("artifacts/ui-profiles/my-app"))  # 再载入移动端扩展 token，返回缺失项
o = [m.phone(0, 0), m.statusbar(0, 0)]
nb, nh = m.navbar(0, m.H_STATUS, title="<标题>", sub="<统计副标题>",
                  right=["search", "select"])     # 右侧最多 2 个图标
```

明暗两种档案都实测可用（缺失的层次色按主背景推导，不会撞色）。


### 三件容易漏但决定「像不像」的事

1. **主色可能不止一个且分工严格。** 很多产品有品牌色（Logo、AI 能力、装饰渐变）和功能色（按钮、链接、选中态）两套。模型靠「参考风格」只会挑一个色到处用，这是 AI 味最上游的来源。采样时留意 Logo 附近和按钮的颜色是否不同。
2. **中性文字通常三档**（正文/辅助/占位）。三档齐全信息层次才对。
3. **克制程度本身就是设计语言。** 成熟 B 端产品几乎不用阴影、靠 1px 边框分层、字重只用 400/500、圆角 4~8px。截图里没有厚阴影和大圆角，生成时也绝不能加。

### 档案产物

写到 `artifacts/ui-profiles/{产品名}/`，模板见 `assets/`：

- `tokens.css` —— 全部设计变量，**唯一的颜色来源**
- `components.css` —— 组件样式，**只允许引用 tokens 变量**
- `icons.svg` —— 线性图标 sprite（`assets/icons-base.svg` 有 55 个通用图标可作起点）
- `profile.md` —— 布局骨架、信息密度、交互范式、文案语气、**采样置信度**

图标集不是可选项。**给足图标是结构性消灭 emoji 的手段** —— 嘴上说「不要用 emoji」没用，模型需要图标时手边没有就会退回 emoji。

字段说明见 `references/ui-profile-schema.md`。

## ③ 画面清单（澄清关口）

PRD + 截图 → **先列画面清单给用户过一眼**，再动手画。

这一步最容易理解偏差，而此时改最便宜 —— 改一行清单 vs 重画一版画板。清单同时暴露 PRD 的洞，这对 PM 本身就有价值。

清单结构：按流程分组，每组列出逐帧。每帧写清：

| 字段 | 说明 |
|---|---|
| 帧号 | A1、A2… 按交互顺序 |
| 画面 | 一句话说明这帧是什么状态 |
| **与上一帧的差异** | 关键 —— 逐帧的本质是「每帧只变一处」 |
| 依据 | PRD 章节号 / 设计图 |
| 保真度 | 高保真 / 中低保真 |

同时单列一节「**PRD 里没写清、需要确认的地方**」。常见的洞：控件能否关闭、多轮场景是否保留、失败态未定义、规则与示例自相矛盾。

**不要把纯规则表画成界面。** 如果 PRD 有一张「输入 → 输出」的规则示例表，那是文档内容，不是画面；画板上该出现的是这些规则作用后的真实界面。

## ④ 逐帧线框图

**产物是一张 SVG**（多帧横向铺开在同一画布上）。怎么分享由你决定：直接发 SVG / 转 PNG、拖进任意协作白板（Figma、FigJam、Miro、tldraw 等都能导入 SVG）、或用 `scripts/whiteboard_publish.py` 发到飞书画板（**可选**，需要飞书环境，见「发布」一节）。

**不接画板也完全可用** —— 生成 SVG 后用 `--dry-run` 出本地预览图核对即可，后面所有约束（安全子集、几何校验）照样有意义：它们保证这张图在任何白板里导入后都不会错位。

这是最容易做错的一步，先说清做什么、不做什么。

### 画的是真界面，不是需求说明

**每一帧都是一个完整的产品窗口**：顶栏、侧边栏、内容区、真实控件、真实文案、真实数据。看上去应该像产品截图。

**不要**在画板上排写着「区域 A：KPI 指标卡 ×4」「位置：工具栏右侧」「需新增」的文字卡片。那是 PRD 的图形化排版，评审时说不清交互 —— 这是本 skill 迭代中被明确否掉的做法。

### 交互靠逐帧演示，不靠文字描述

同一界面连续几帧，**每帧只变一处**：光标移动 → 控件出现 → 面板内容变化 → 数据落位。

不要画一个静态框写「点击后展开下拉」，而是画出**下拉展开的那一帧**。生成中、diff 预览、报错、选中、hover、toast 都各是独立一帧。

### 突出重点用图纸语言，不改产品比例

**这条是硬教训。** 需求重点在侧边面板时，不要把面板从 27% 拉到 55% —— 比例一改就画出了真实产品里不存在的界面，线框图失去参考价值。

正确做法：
- **按实测比例画**。量参考图的像素，别估。（本 skill 迭代中实测某产品 AI 面板占 27.3%，而我一度拉到 55%，被用户直接指出「比例失调很奇怪」）
- **紫色强调框标重点**：`emphasis_frame` 框整帧 + `emphasis_area` 框局部控件
- **非重点区域可 ghost 化**：`table_ghost` 把表格降为灰条结构底，保留上下文但不抢注意力

### 图纸语言约定

| 元素 | 做法 | 构件 |
|---|---|---|
| 阶段分组 | 黑色箭头形横幅，跨在该组画面上方 | `stage_banner` |
| 帧标识 | 深色小标签，帧左上角 | `frame_tag` |
| 保真度 | 深色小标签，标在帧组左侧 | `fidelity_tag` |
| 批注 | 紫色小字，**放帧下方横向铺开**（放右侧会挤占画面宽度） | `anno` |
| 帧间跳转 | 细紫线 + 极短动作标签（连线是辅助，不该抢戏） | `flow_arrow` |
| 交互落点 | 鼠标光标 | `cursor` |

### 用构件库拼装，不要手写 SVG

高保真每帧 100~200 个元素，6 帧就上千个。手写必然坐标错位、配色漂移。

```python
import sys; sys.path.insert(0, "<skill>/scripts")
import wireframe_kit as k

r = k.use_profile("artifacts/ui-profiles/my-product")   # 载入档案 tokens
print(r)      # {"loaded": 13, "missing": [], "theme": "dark"} —— theme 会自动判
print(k.missing_tokens())                               # 缺哪些 token，值得回去补

W, H, SB, PANEL = 1180, 660, 150, 322                # 按实测比例
o = [k.win(0, 0, W, H)]
o.append(k.topbar(0, 0, W, ["<空间>", "<文档名>"],
                  right_btns=[("分享", True)], right_icons=["bell", "search"]))
o.append(k.sidebar(0, 34, SB, H - 34, TREE, active="<当前项>",
                   added="<本次新增项>"))            # added 加紫标记，研发一眼看出改动
o.append(k.table_ghost(SB, 90, W - SB - PANEL, H - 90, COLS))
o.append(k.panel(W - PANEL, 34, PANEL, H - 34, "<面板标题>", "<副标题>"))
...
svg = k.svg_doc(total_w, total_h, "".join(o))
```

构件分两类，**职责严格分开**：产品界面构件（`win/topbar/sidebar/tabs/toolbar/table/table_ghost/panel/input_box/bubble/chip/card/status_row/node_card/node_chain/toggle/zoom_bar/icon`）按实测比例画真实产品；图纸语言构件（上表那些）画标注。想突出重点时用后者，绝不动前者的尺寸。

AI 对话类需求另有一组结果组件：`chart_card`（折线/柱状图卡片，`hover_idx` 可画 tooltip 态）、`base_table_card`（窄面板里的数据表，自动等比缩列 + 超宽截断 + 滚动条）、`dark_menu`（深色二级弹出菜单，`hl` 标悬停项）、`toast`。窄面板放图表和表格的轴标签重叠、列宽溢出问题这几个构件已处理好，不要重写。

`icon()` 提供 20 余种常见线性图标，都是 B 端桌面风格。**不要用空方框占位** —— 那会让整帧看起来像未完成的草稿（本 skill 迭代中犯过这个错）。缺图标就照同样的 stroke 风格加一个分支；移动端往往要补一整组（实测补了 31 个），写在自己的扩展文件里、`icon()` 兜不住的名字再转交它即可。

**用 `import wireframe_kit as k` 访问 tokens，不要 `from wireframe_kit import T`。** `T` 是模块级字典，虽然 `use_profile()` 已改成原地更新（`T.clear()/update()`）而非重新绑定，但走 `k.T[...]` 永远不会有引用失效的问题。这个坑犯过一次：深色档案画出来整套是浅色配色，查 SVG 才发现 `fill` 是上一套 token 的值 —— 不报错、静默出错，只有渲染核对能发现。

`table()` 行数按可用高度自动撑满 —— 真实产品一屏十几到几十行，留大片空白会一眼假。

`assets/frame-generator-skeleton.py` 是可直接跑的生成器骨架（帧函数 + 排布 + 尺寸常量），复制到工作目录改写比从零写快得多。逐帧的完整规范、比例实测量法（用列方差找面板边界）和 13 项错误清单见 `references/frame-by-frame.md`。

### 发布

```bash
python3 scripts/whiteboard_publish.py --svg flow.svg --check            # 只做校验
python3 scripts/whiteboard_publish.py --svg flow.svg --dry-run          # 校验 + 本地预览图
```

以上两条**不需要任何在线服务**，任何环境都能跑。下面这条把图发到飞书画板，**需要飞书环境和 `lark-cli`**（字节内部工具）——没有的话跳过，直接把 SVG 或预览 PNG 分享出去，或导入你团队用的协作白板：

```bash
python3 scripts/whiteboard_publish.py --svg flow.svg --title "需求名 · 线框图"
```

脚本负责：安全子集校验 → 几何校验（`--check` 必须 0 error）→ 转节点 → 探测授权 → 创建文档与画板 → 写入 → **回查服务端节点数** → 回读渲染图。

**必须看「回查确认」那一行。** 写入接口的返回值不可信：`created_node_ids` 在幂等命中时会回放上次请求的结果，于是脚本打印「成功 751 个节点」而新画板一个节点都没有 —— 用户打开就是一片空白。脚本现在会实查服务端并在为空时直接报错，但如果你自己调 `lark-cli whiteboard +update`，记得幂等键必须带上画板 token（只用「文件名 + 节点数」时，同一份 SVG 重发到新画板会被判成重复请求）。

**画板的能力边界必须先知道**：无阴影、字体锁死、圆角被量化、边框宽度只有 4 档、无径向渐变/模糊/裁剪蒙版。所以**不要用圆角或阴影承载语义**（靠圆角区分状态，转换后就没了）。禁用 `filter`/`radialGradient`/`clipPath`/`mask`/`foreignObject`/`<image>`。详见 `references/whiteboard.md`（含实测踩坑与完整命令）。

**不要用负坐标。** 图纸标注（`emphasis_area` 的引线标签等）落到画布左侧负区间时，实测会出现整片不渲染。整图右移让所有坐标为正即可。

节点数 751 实测可一次写入。真要分批时注意：不带 `--overwrite` 是追加，会坐标重叠。

服务端渲染图是**异步生成**的，刚发布就导出可能拿到全白图。判断有没有写进去要看回查的节点数，不要靠渲染图 —— 我在这上面误判过两次（先怀疑渲染延迟、再怀疑节点数超限），实际都是幂等键的问题。

## ⑤ 可交互 HTML demo

### demo 演的是过程，不是结果

**这条最容易做错，而且做错了自己看不出来。**

失败长这样：打开 demo 就是一屏「AI 已经答完」的终态 —— 图表在那儿、结论在那儿、按钮能点。看着挺完整，其实等于把线框图的某一帧做成了网页。评审的人问「AI 是怎么一步步给出来的」，demo 答不了。

原因是「可交互」这个词有歧义：**控件能响应点击 ≠ 演示了交互过程**。前者是终态加事件监听，后者是时间轴。这两件事的差距，就是第 ④ 步费力做逐帧线框图的全部理由 —— 如果 demo 只给终态，那它比线框图信息更少，白做。

正确做法：**demo 打开后从起点自动演播到终点**，帧序和第 ③ 步画面清单一致。

以 AI 类需求为例，起点是空会话，不是回答完的会话：

| 该演的过程 | 具体做法 |
|---|---|
| 用户输入 | 问题**逐字敲进**输入框，发送按钮由禁用变可用 |
| 提交 | 点击（可加涟漪）→ 问题变气泡上屏 → 起始页内容退场 |
| 后台处理 | 工具调用行 + spinner「调用中…」，**此时结果必须还没出现** |
| 生成 | 文字**流式吐出**（末尾闪烁光标），不是整段瞬现 |
| 结果落位 | 图表折线**按路径描画**、表格**逐行渐显**、数据标签随后亮起 |
| 后续可选操作 | 自动演示一次关键 hover / 点击，然后交还给用户手动点 |

其他需求类型同理：表单类演「填写 → 校验报错 → 修正 → 提交成功」，列表类演「筛选 → loading → 结果更新 → 空状态」。**凡是 PRD 里写了「中间态」「loading」「生成中」的，都必须在时间轴上占一段**，否则这些状态等于没设计。

三个配套设施，缺了过程就看不清：

- **模拟光标**：自动演播时用户不知道「点了哪里」，画一个跟随移动的光标 + 点击涟漪
- **帧号指示**：控制条实时显示当前帧（A1/A2/A3…），与线框图帧号对齐，评审时能互相指认
- **「重播」+「跳到结果」两个按钮**：评审现场经常不想等动画，必须给跳过入口；讲解时又要能重播

动效必须克制到产品级：位移 4px 以内、时长 200~300ms、缓动用 `ease-out`。**弹跳、缩放、渐变流光都是 AI 味**，真实 B 端产品不这么动。

### 必须是单个自包含 HTML

tokens、components、图标 sprite、数据全部内联，**不允许任何外部依赖**。

理由不是「否则做不像」，而是**否则发出去打不开**。这个坑很隐蔽：多文件方案在完整目录下双击能用（普通 `<script src>` 在 `file://` 同目录可加载），生成方自测一切正常；但 PM 的高频动作是「把 demo 发到群里」—— 只发主文件，接收方打开就是空白页 + 一堆 404。另外 `fetch()` 在 `file://` 下被浏览器直接拦截，数据必须写成字面量常量。

`assets/demo-skeleton.html` 是按此约束搭好的骨架，含时间轴播放器。

### 生成规则

- **颜色和尺寸只来自 tokens 变量。** 需要档案里没有的颜色时先问「能不能用现有 token 表达」，确实需要就补进档案并说明理由，而不是在页面里写死。
- **图标只引用 sprite，禁用 emoji。** 缺图标按已有风格补进 sprite。
- **只做需求涉及的页面和交互**，但涉及到的那条链路要演完整。
- **数据要像真的** —— 用 PRD 里的真实字段名、业务词汇、合理量级。占位式的「示例 1 / 张三 / Lorem ipsum」会立刻失去说服力。
- **信息密度对齐产品。** B 端表格行高 32px 左右、一屏十几行是常态；行高 60px 一屏五行即使配色全对也一眼假。

### 档案里没有的控件

新需求必然需要新控件。按档案的设计逻辑**推导**，而不是凭空发明：沿用同样的边框色、圆角刻度、字重策略、选中态表达方式。如果产品用「底色变化 + 文字变色」表示选中，新增的 Tab 就也这么做，不要突然改用下划线加粗。

推导所得的控件写进 `components.css`，并在 `profile.md` 标注「未经截图验证」。

一个真实例子：某需求要做 diff 预览，行业默认是红绿加减色，但档案的语义范式是「浅底色 + 统一深灰文字」、全站无饱和红绿 —— 正确做法是用中性三档承载层次（原值三级灰加删除线、新值一级灰），并写清推导依据。

## ⑥ 自检

```bash
python3 scripts/check_demo.py --html demo.html                    # 单文件可用性 + 配色规范
python3 scripts/check_profile_drift.py --profile <档案> --target demo.html
python3 scripts/screenshot.py --html demo.html --out /tmp/s.png   # 渲染核对
```

`check_demo.py` 查字面量色值（`:root` 里的 token 定义自动排除，那是颜色源头）、emoji、`fetch()`、外链资源、图标引用完整性、异常圆角与阴影。

`check_profile_drift.py` 查同名 token 取值是否一致、有无档案外新增颜色、是否根本没在复用档案。**新增颜色是最需警惕的信号** —— 那是配色逐轮漂移的机制。

`screenshot.py` 用 `file://` 加载（正是用户双击的方式），支持 `--click` 多状态截图。

**渲染核对不是形式主义。** 实测中它拦下过静态检查完全查不出的问题：图标全部消失、条形图不可见、预填了会让评审误判的数据。画板同理，发布后要看回读的服务端渲染图。

拿渲染结果和原始截图逐项比对：

- 配色是否有档案外的颜色
- 圆角与阴影的克制程度是否一致（有没有偷偷加厚）
- 字号字重层级是否一致（有没有堆 600/700）
- 信息密度是否一致（行高、一屏信息量）
- 图标风格是否统一（粗细、端点、有无混入面性图标、**有无空方框占位**）
- 有没有任何 emoji

### 过程核对：沿时间轴抓帧

静态检查和单张截图都查不出「只有终态」这个毛病 —— 截图恰好截在结束后，看起来一切正常。必须**沿时间轴抓多个瞬间**，逐帧断言中间态真实存在：

```python
# 关键是断言「中间态」，而不是只断言终态
pg.goto(url); pg.wait_for_timeout(300)
assert "Hi，" in pg.locator("#stream").inner_text()          # 起点：空会话
pg.wait_for_timeout(1100)
v = pg.locator("#ask").input_value()
assert 0 < len(v) < len(FULL_Q)                              # 打字到一半
pg.wait_for_function("() => document.querySelector('.spin')")
assert pg.locator(".viz-card").count() == 0                   # 调用中，结果还没出
pg.wait_for_selector(".viz-card")
assert pg.locator("tbody tr.in").count() < TOTAL              # 逐行落位中
```

`assert 中间态 count() == 0 / < 总数` 这类断言是核心 —— 它们证明过程真的分了步骤，而不是一次性渲染完再加个淡入。

**两个会让测试假失败的坑**（都实际踩过）：

1. **不要写死等待毫秒**，用 `wait_for_function` 等状态出现。`wait_for_selector` 自身返回耗时不确定，紧跟一个 `wait_for_timeout(80)` 很容易越过整段短动画。
2. **短动画要在页面内自采样**，别用 Playwright 反复 `count()` —— 每次跨进程调用都有开销，几百毫秒的动画会被采样本身吃掉：

```python
pg.evaluate("""() => {          # 让页面自己记录序列，再一次性取回
  window.__seq = [];
  const id = setInterval(() => {
    window.__seq.push(document.querySelectorAll('tbody tr.in').length);
    if (window.__seq.length > 400) clearInterval(id);
  }, 25);
}""")
seq = pg.evaluate("window.__seq")
assert seq[0] < TOTAL and seq[-1] == TOTAL      # 演出了过程，且最终落满
assert all(b >= a for a, b in zip(seq, seq[1:]))  # 单调递增，没有回跳
```

顺带一个实现坑：逐行落位写成 `setTimeout(..., per * i)` 时第 0 行 `delay=0`，会与容器同步出现 —— 行数少时整表看着像一次性渲染。要写 `per * (i + 1)`。

playwright 不可用时如实说明「静态检查已过，未做渲染核对」，不要假装验证过了。

产物路径用 Markdown 引用格式给出：

- 线框图（SVG / PNG，或已发布的白板链接）
- 可交互 demo（`.html`，单文件可分享）
