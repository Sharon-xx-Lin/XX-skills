# UI 档案（UI Profile）结构说明

档案是这套方法的核心资产：把截图里的设计语言固化成机器可读的文件，让后续生成从"凭感觉创作"变成"照表查询"。

**存放位置**：`artifacts/ui-profiles/{产品名}/`

档案属于用户的资产，不放进 skill 目录。不同产品经理负责不同产品，档案必须彼此隔离。做过一次后，后续需求直接复用，无需重新上传截图——这是档案最主要的收益。

```
artifacts/ui-profiles/{产品名}/
├── tokens.css        全部设计变量（唯一的颜色来源）
├── components.css    组件样式（只引用 tokens）
├── icons.svg         线性图标 sprite
├── profile.md        布局骨架、密度、语气、采样来源与置信度
└── samples/          原始截图与采样点位配置（便于日后复核和扩充）
```

---

## tokens.css

唯一的颜色和尺寸来源。分组建议：

```css
:root {
  /* 品牌与功能色 —— 注意区分职责 */
  --brand-*          品牌色：Logo、AI 能力、装饰性渐变
  --primary          功能色：主按钮、主操作
  --primary-hover
  --primary-bg-weak  选中态底色
  --link

  /* 中性文字三档 —— 三档齐全信息层次才对
     深色主题常有四档（多一档极弱信息，如日期），且一级最亮、三级最暗，
     与浅色完全相反。按实际采样写，不要套浅色的档位数。 */
  --text-1           一级：标题、正文、表格数据
  --text-2           二级：副标题、表头、分组标签
  --text-3           三级：占位符、行号、禁用态
  --text-4           四级：深色主题常见的极弱信息（可选）
  --text-on-primary

  /* 背景层
     深色主题这里是「层次递进」而非「几种平级底色」：
     根背景 → 卡片 → 引用块/输入框 → 选中块，每层朝白提亮一点。
     通用工具按 --bg-input / --bg-hover 这类标准名去找，产品自己叫
     --bg-card / --bg-quote 时记得加一个同值别名，否则工具取不到会退回兜底值。 */
  --bg-body / --bg-sidebar / --bg-input / --bg-hover
  --bg-selected-*    选中态可能有多种（中性/品牌向）
  --bg-chip

  /* 边框 —— 多数产品全站就一个发丝线色值
     但有些产品（尤其深色主题）一条边框都不用，纯靠背景层次分层。
     扫描线法测出亮度差只有 1~2 时，那不是采样失败，是真的没有边框 ——
     照实记下来，这本身就是设计语言，生成时也不要凭空加边框。 */
  --border
  --border-strong

  /* 语义标签配色 —— 底色与文字成对 */
  --tag-*-bg
  --tag-text         注意：常常是所有标签共用一个深灰文字色

  /* 圆角刻度 —— 有层次，不是统一值 */
  --radius-sm/md/lg/xl/pill

  /* 间距 —— 通常是 4px 基准栅格 */
  --sp-1..--sp-8

  /* 字体 */
  --font
  --fs-*             4~5 档够用
  --fw-normal/medium/bold    B 端多数只用 400/500

  /* 阴影 —— 成熟 B 端产品这里通常极其克制 */
  --shadow-*

  /* 控件尺寸 —— 决定信息密度，很关键 */
  --h-control / --h-row / --h-topbar / --w-sidebar
}
```

**填写要点**

- 颜色值全部来自 `scripts/sample_ui.py` 的采样结果，不要手填估计值
- 同语义多点采样后取中位数（脚本会给建议值）
- 截图里没出现的 token 可以留空或按刻度推导，但要在 profile.md 里标注是推导所得
- `--h-row`（表格行高）这类尺寸务必对着截图量，它直接决定信息密度像不像

## components.css

组件样式层。**铁律：只允许引用 tokens 变量，不允许出现任何字面量颜色值。**

这条约束是"反 AI 味"最有效的结构性防线——一旦允许直接写色值，配色就会漂移回模型的默认审美。`scripts/check_demo.py` 会自动扫。

建议覆盖的组件（按截图里实际有的写，没有的不用硬凑）：

```
布局骨架     .app .topbar .sidebar .main .content
导航         .nav-item（含 hover/选中态）.nav-group-title .nav-divider
按钮         .btn 及变体（primary / text / icon / chip 胶囊）
输入         .input .search .prompt-box
卡片         .card .card-title .card-sub
表格         .table th/td .row-index .cell-link（注意行高）
标签         .tag 及各配色变体
标签页       .tabs .tab
工具栏       .toolbar .toolbar-divider
面板         侧边面板、抽屉
头像/徽标    .avatar .badge
面包屑       .breadcrumb
```

**选中态的表达方式要跟产品一致。** 如果产品用"底色变化 + 文字变色"表示选中，新增的 Tab 组件也该这么做，不要突然改用"下划线 + 加粗"——这种不一致比配色错误更容易被察觉。

## icons.svg

线性图标 sprite。**这不是可选项** —— 给足图标是结构性消灭 emoji 的手段。

```html
<svg xmlns="http://www.w3.org/2000/svg" style="display:none">
  <symbol id="i-name" viewBox="0 0 16 16"><path d="..."/></symbol>
</svg>
```

规范：
- 统一 `viewBox`（建议 `0 0 16 16`）
- `stroke="currentColor"` + `fill="none"`，颜色由 CSS 控制
- 统一 stroke 宽度（按产品风格定，常见 1.5~1.8）
- 统一 `stroke-linecap` / `stroke-linejoin`
- 命名用 `i-` 前缀 + 语义名

`assets/icons-base.svg` 提供 56 个通用图标（导航、操作、表格、图表、状态、文件类），可直接用作起点，按产品风格调 stroke 粗细和端点样式。

缺图标时按已有图标的风格补一个（同 viewBox、同 stroke、同端点），**不要退回 emoji**。

## profile.md

记录无法用 CSS 表达的部分。建议结构：

```markdown
# {产品名} UI 档案

## 基本信息
端形态、产品定位、截图来源与日期

## 布局骨架
侧边栏宽度、顶栏高度、内容区栅格、面板宽度
主要页面的区域划分方式

## 信息密度
表格行高、一屏行数、卡片间距、控件高度
（这一节很关键，密度不对即使配色全对也一眼假）

## 双主色分工
品牌色用在哪、功能色用在哪
（如果产品只有一个主色，写明即可）

## 交互范式
选中态如何表达、hover 如何表达、
主操作按钮的位置习惯、弹窗/抽屉/侧边栏的使用场景

## 文案语气
中英混排习惯、按钮文案风格、空状态文案风格
真实字段名与业务词汇表（生成 demo 时的数据来源）

## 采样来源与置信度
| token 组 | 来源 | 置信度 |
|---|---|---|
| 中性文字三档 | 2 张截图交叉验证，各 3 点 | 高 |
| 边框色 | 9 处扫描线，极差 2 | 高 |
| Tab 组件样式 | 截图未出现，按选中态逻辑推导 | 待校正 |

## 待补充
还需要哪类截图能提升准确度（hover 态、弹窗、空状态、表单页…）
```

**置信度这一节要如实写。** 只有 1 张截图就说清覆盖范围有限，哪些是推导所得。用户知道边界才能有效校正，含糊其辞反而会让他们在错误的地方浪费信任。

## samples/

存原始截图和采样点位配置（`points.json`），便于：
- 日后复核某个 token 的来源
- 补充新截图时沿用已有点位配置
- 换人接手时能看懂档案是怎么来的
