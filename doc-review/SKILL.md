# 文档审查

帮用户审查一篇文档,找出问题、给出定位和简单修改建议,**但不改动原稿**。

## 这个 skill 的边界(先读这一段)

审查和改写是两件事。用户要的是一份"体检报告",不是一份被你重写过的稿子。所以:

- **只报告,不落笔。** 每条问题给出定位 + 建议改法供用户参考,但绝不直接修改原文、也不输出"改好的版本"。
- **不碰内容层。** "把这句话的意思表达得更好""这个论点可以更有力""换个角度写会更打动人"——这类涉及**改变原意让它更好**的判断不在范围内。本 skill 只管文字对不对、通不通、前后合不合、结构全不全,不管观点好不好。
- **区分硬错和主观建议。** 错别字、标点、加总对不上是**硬错**,高置信,该明确指出;"啰嗦""AI 味"是**主观建议**,见仁见智,当参考。报告里把两者分开,用户才能放心信任硬错、自行斟酌建议。这个区分是本 skill 的核心价值,不要把两类混在一起报。

## 流程

### 第 1 步:拿到文档内容

按来源选择读取方式。**读不到就明确告诉用户,不要静默失败或假装读到了。**

| 来源 | 怎么读 |
|---|---|
| 飞书文档(链接) | 用 lark-doc / lark-sheets / lark-base 相关 skill 读取。这是最常见的场景。 |
| Word(.docx) | 用 `docx` skill 或 pdf/文本提取;本地文件也可用 Bash 提取纯文本。 |
| Notion | 若用户贴的是公开分享链接,用浏览器/抓取读取;若是私有页面无法访问,提示用户导出为 md/docx 或直接粘贴内容。 |
| 本地文件(md/txt/docx) | 直接用 Read / Bash 读取。 |
| 直接粘贴的文本 | 已在对话里,直接用。 |

**无法访问时**:明确说明读不到的原因(权限/链接失效/格式不支持),并给出可行替代——"请把文档导出为 Word/Markdown 上传,或直接把正文粘贴进来"。不要凭空猜内容。

拿到内容后,先快速通读一遍,对文档的**类型和预期结构**有个判断(是方案/周报/PRD/对外文案/说明文档?),因为"板块遗漏"和"标题与内容匹配"的审查都依赖对"这类文档应该长什么样"的理解。

**当实质内容承载在图片里时(诚实优先)**:有些文档的关键信息(配置、界面、示意图、被截图的表格/数据)是以图片而非文字呈现的。纯文字审查覆盖不到这些像素内容,此时不要默默略过、更不要假装看过。原则是:

- **先诚实声明覆盖范围**:说明文字审查覆盖的是正文与可读文本,图片内的内容未经核对。
- **再主动提议补审**:对承载关键信息的图片,提议做 OCR 后再补一轮审查,由用户决定是否要做。

是否声明、声明多细,取决于图片是否真的承载了实质内容——图片只是装饰或补充说明时不必强调。不要把这条变成每篇必附的套话。

### 第 2 步:分层审查

从字面到篇章逐层扫,**全部扫完**。分层不是为了取舍,而是因为越靠近字面越客观、越靠近篇章越依赖判断,分层能让你在报告里如实标注每条的置信度。

下面每一项都给了"在找什么",照着扫。**能用脚本客观判定的(标点、全半角、残留占位符、格式),优先写个小脚本跑,比肉眼可靠。**

#### L1 文字层(高置信,基本都算硬错)

- **错别字**:形近/音近别字、多字漏字、明显手误。
- **标点与中英文混排**:中文正文里混用英文逗号句号(`,` `.` 而非 `,` `。`)、中英文之间空格不一致、全半角混用、成对标点(引号/括号)不闭合、省略号/破折号写法不规范。
- **格式一致性**:标题层级跳级(如 ## 直接跳到 ####)、列表符号不统一、有序列表编号断档或重复、缩进/空格不一致、同类元素样式忽大忽小。
- **表格结构一致性**:表格是二维结构,一致性问题靠通读正文容易漏,值得专门看。留意各行列数是否对齐、表头是否完整、同一列的数据类型是否一致、跨行分类归属是否错位(如某行归错了分类、多级表头下的子项挂错父项)。**这里要按硬错/主观建议分开判**:列数错位、表头缺失、分类明显挂错这类**客观错位算硬错**;而"表格该拆成几节""排布方式换一种更清晰"这类**编排风格属主观建议**,归到 L2/L3 的主观区。
- **残留占位符**:`TODO`、`XXX`、`待补充`、`(此处待定)`、`【】`、示例/模板文字没删干净、`Lorem ipsum`、明显是草稿留下的批注。

#### L2 语句层(硬错与主观建议混合,注意分开标注)

- **语病**(硬错):成分残缺、搭配不当、句式杂糅、主宾不搭、关联词误用、指代不清。
- **术语 · 称谓一致性**(硬错):同一事物前后叫法不一(如"用户/客户/使用者"混用)、缩写忽全称忽简称、大小写不统一(如 `iOS`/`IOS`/`ios`)、产品名/人名写法前后不一。
- **啰嗦 / 废话**(主观建议):同义反复、可删的冗词、绕圈子不说重点、为凑篇幅的套话。给出"可精简为 X"的建议,但不强制。
- **AI 味**(主观建议):这是最主观的一项,只标记**典型信号**,不做风格重写:
  - 排比堆砌(连续的"不仅…而且""既…又…"、三四个短句强行排比撑气势);
  - "不是…而是…"这类套话句式反复出现;
  - 空泛形容词堆砌("强大的""全面的""深入的""极致的"却不落到具体);
  - 生硬晦涩、翻译腔或不像人话的词(如"进行了一个 X 的操作""赋能""抓手""颗粒度"在不必要处滥用、生造词)。
  标记出来 + 简单说明为什么读着像 AI,让用户自己判断要不要改。

#### L3 篇章层(依赖全文判断,大多算硬错,口径类除外)

- **前后矛盾**:同一事实前后说法打架。特别留意**数据/事实自洽**——分项加总对不上总数、前文说"3 点"后文列了 4 条、同一数字/日期/金额前后不一致、图表与正文对不上。还有一类隐蔽的可验算关系:**总量应等于分项数 × 每项数量**(如"共 N 道题,各类 M 道"就该满足 N = 类数 × M),遇到这种表述顺手做一次乘/除法验算。**这类靠肉眼最容易漏,值得单独逐一核对,能算的用脚本算。**
- **正文与定义表/schema 交叉一致性**:当文档自带"字段说明表""术语表""参数定义表"时,交叉核对正文里出现的字段名/术语,是否都能在定义表中找到条目;反过来定义了却全文没用到的也值得一提。正文引用了表里查无此项的字段(或名字对不上)是常见且易漏的硬错。
- **板块遗漏**:按这类文档的常规结构,该有的部分缺了(如方案缺"风险/成本"、PRD 缺"验收标准"、复盘缺"改进项")。基于文档类型判断,而不是套死模板;文档明确是初稿/片段时,不要硬扣"缺板块"。
- **标题与内容不匹配**:小节标题说 A,正文却在讲 B;或标题承诺的内容正文没覆盖到。这是"遗漏"的隐蔽变体。
- **规则/定义多处复述、口径不一致**(主观建议):同一条规则或定义在文档多处出现(如速览、表格、正文都讲了一遍打分规则),各处口径不完全一致、有的版本漏了关键维度。这不影响单处的正确性,只影响阅读时的一致体验,**归主观建议**,提示以某一处为准、其余指向它,精简对齐。

### 第 3 步:输出审查报告

默认**直接在对话里**给出结构化报告(除非用户要求沉淀成飞书文档)。用下面的模板。核心原则:**硬错和主观建议分区**,每条都要**可定位**(引用原文片段或位置),这样用户能一眼找到、快速核对。

```markdown
## 审查报告:<文档标题>

> 文档类型:<你的判断> ｜ 已扫描:L1 文字 / L2 语句 / L3 篇章

### 一、硬错(建议修正,高置信)

按严重度或位置排序。每条格式:
- **[类型]** 原文:「<引用出问题的片段>」→ 问题:<一句话说清>。建议:<改法>。

示例:
- **[错别字]** 原文:「制定相关的政策措施」→ "制定"应为"制订"(此处指拟定草案)。建议:改为"制订"。
- **[数据矛盾]** 原文:「三大板块…」后文实际列出 4 项。建议:核对是"三大"还是"四大",统一表述。
- **[标点]** 原文:「完成了目标, 效果显著.」→ 中文正文混用英文逗号句号。建议:改为「,」「。」。

### 二、主观建议(供参考,可斟酌)

- **[类型]** 原文:「<片段>」→ 观察:<为什么读着有问题>。可考虑:<方向,不强制>。

示例:
- **[AI 味]** 原文:「我们不仅要拥抱变化,更要引领变化,在变化中创造价值」→ 排比+空泛,读着像 AI 生成。可考虑:落到具体做了什么。
- **[啰嗦]** 原文:「基于以上所述的这些原因和因素」→ 可精简为「基于以上原因」。

### 三、结构与完整性

- 板块遗漏:<有/无,缺了什么>
- 标题与内容匹配:<有无不符的小节>

### 小结

<1-2 句:整体质量印象、最该优先处理的几类问题。不吹捧、不空泛。>
```

**报告写作注意**:
- 没问题的层次也要说一句"未发现明显问题",让用户知道你确实扫了,而不是漏了。
- 硬错要给准确定位和明确改法;主观建议措辞留余地("可考虑""读着像"),因为这些本就见仁见智。
- 别为了凑数把没问题的地方硬说成问题。找不到就是干净,如实说。
- 数量大时按类型归组、可折叠,但不要因为多就省略——审查报告的价值就在全。
