# doc-review

轻量级文档审查 skill。审查一篇文档的**文字质量**与**结构完整性**,产出**分层的审查报告**并给出简单修改建议,**但不改动原稿**。

## 它做什么

给用户一份"体检报告",而不是一份被重写过的稿子。审查覆盖三层:

- **L1 文字层** —— 错别字、标点与中英文混排、格式一致性、表格结构一致性、残留占位符。
- **L2 语句层** —— 语病、术语/称谓一致性、啰嗦废话、AI 味(排比堆砌、"不是…而是…"套话、空泛形容词、生硬翻译腔)。
- **L3 篇章层** —— 前后矛盾(含数据加总/数量/日期不自洽、总量=分项×单量的验算)、正文与定义表/schema 交叉一致性、板块遗漏、标题与内容不匹配、同一规则多处复述口径不一致。

## 它不做什么

- **不改原稿** —— 只报告问题 + 给建议改法,绝不直接修改原文或输出"改好的版本"。
- **不碰内容层** —— 不做"把意思表达得更好""论点更有力"这类改变原意的判断。只管文字对不对、通不通、前后合不合、结构全不全,不管观点好不好。

## 核心设计

**硬错与主观建议分区**是这个 skill 的核心价值:

- **硬错**(错别字、标点、加总对不上、字段查无定义)—— 高置信,明确指出。
- **主观建议**(啰嗦、AI 味、编排风格、口径不一致)—— 见仁见智,当参考。

报告里把两者分开,用户才能放心信任硬错、自行斟酌建议。

## 支持的输入

飞书文档、Word(.docx)、Notion、本地 md/txt/docx,以及直接粘贴的文本。**读不到就明确提示用户**,不静默失败。关键信息承载在图片里时,先诚实声明文字审查的覆盖范围,再主动提议对关键图做 OCR 后补审。

## 用法

在支持 skill 的环境中,当用户表达"审查/校对/检查/挑错/review 这篇文档""看看有没有错别字和语病""这篇有没有 AI 味""前后有没有矛盾/漏掉的部分"等意图,或贴来文档链接/大段文本时自动触发。

## 目录结构

```
doc-review/
├── SKILL.md                 # skill 主体:触发描述 + 边界 + 三步审查方法论(运行时唯一依赖)
├── README.md
├── .gitignore
└── evals/                   # 评估套件(开发/回归用)
    ├── evals.json           # 测试用例:prompt + expected_output + files
    ├── ANSWER_KEY.md        # 每篇测试文档的预埋问题清单(标准答案)
    └── files/               # 合成测试文档(含预埋问题 + 干扰项,不含真实业务数据)
        ├── weekly_report.md
        ├── marketing_copy.md
        └── tech_design.md
```

运行时只需 `SKILL.md`;`evals/` 仅用于迭代和回归测试。
